1.3 Models vs applications: what you actually build

The model remembers nothing between calls. Everything a GenAI product seems to "know" about you, your conversation and your data is put there by the application, on every single request. This lesson makes that split concrete, then shows why outputs vary and how you test something that varies.

~30 minModule 1Python + engineering

1The model is a stateless function

Definition: a component is stateless when it keeps nothing from one call to the next. Every call starts from zero, and the output depends only on what that call sends in.

An LLM in use is exactly that. You send it a sequence of tokens, it runs the predict → pick → append loop from Lesson 1.2, and it returns tokens. When the call ends, nothing about it is kept inside the model. Its weights (the learned numbers) were fixed when training finished, and they do not change while you use it.

reply = model(everything in this request)The only input is the request. There is no hidden second input called "what we talked about earlier".

Two consequences matter

Both follow directly from statelessness, and together they explain most of what an application has to do.

1
The model does not remember your conversation

If you tell a chat model your name in one message and ask for it in the next, it seems to remember. It does not. The chat application stored your first message and sent it again, together with the new one. The model read the name in the request, the same way it would read it in any document.

It also does not learn from your conversation. Correcting it ("no, the balance is 1,250") changes the next reply only because the correction is now part of the request. Start a new conversation and the correction is gone. (Whether a provider later uses your conversations to train a future model is a separate data-policy question, decided by your contract and settings, not by the model.)

2
Everything the model knows about this situation must be in the request

The model has two sources of information only: what it absorbed during training (general knowledge, up to its training cutoff) and what is in the current request. Your customer's invoice, today's date, the user's permissions, the earlier messages: if any of these matter, the application must look them up and put them into the request.

This is why "the model" and "the application" are different jobs. The model turns a request into text. The application decides what goes into the request and what happens to the text that comes out.

≈
Power BI analogy

A DAX measure is evaluated fresh for every visual, using only the filter context it is given right now. It has no memory of what the previous visual showed. An LLM call works the same way: the request is its whole "filter context". If you want it to take something into account, you must put it in.

2What one request contains

A chat model's API does not take one long string. It takes a list of messages, each with a role that says who wrote it, plus some settings. The provider turns the list into one token sequence using the model's chat template (Lesson 2.1), with special tokens marking where each message starts and ends.

RoleWho writes itTypical content
system (some APIs: developer)You, the developerTask, rules, tone, output format. The model is trained to give it high priority.
userThe end user (passed on by your app)The question or instruction
assistantThe model, earlier in the conversationPrevious replies, sent back so the model can see them
toolYour codeThe result of a function the model asked to call (Stage 3)

Besides the messages, a request carries settings: which model, the temperature from Lesson 1.2, and a maximum number of output tokens. On most APIs, input and output share the same context window, so a long input leaves less room for the answer.

What an application typically assembles

In a real product, the "user message" the model receives is rarely just what the user typed. The application builds the request from several sources, in a deliberate order:

InstructionsSystem message: role, rules, output format, what to do when information is missing
Retrieved dataDocument passages or database rows fetched for this question (RAG, Stage 4)
Tool resultsExact values from SQL queries or APIs the model asked for (Stages 3 and 5)
HistoryEarlier messages, possibly trimmed or summarised (section 4)
New messageWhat the user just asked

This assembly step is called context construction (or context engineering). It is where most GenAI engineering effort goes, because the model can only be as good as what it is shown.

i
Engineering principle #2

You do not program the model. You program the request. When an answer is wrong, the first question is: was the information it needed actually in the request?

3Chat memory is the application resending history

Let us measure it. This script plays a six-turn conversation about an invoice. Before each model call it appends the new user message, counts the tokens in everything that will be sent, then appends the model's reply so the next call includes it. The replies are written by hand, so no API is needed; the token counts are real, from the o200k_base tokenizer.

chat_history.py
import tiktoken

enc = tiktoken.get_encoding("o200k_base")

def count(messages):
    # content tokens only; real requests add a few formatting tokens per message
    return sum(len(enc.encode(m["content"])) for m in messages)

system = {"role": "system", "content": "You are a helpful assistant for the finance team. Answer briefly and cite the invoice ID."}
turns = [
    ("What is the status of invoice INV-204?", "INV-204 is unpaid. The balance is 1,250.00 EUR and it was due on 3 November."),
    ("Who is the customer?", "The customer on INV-204 is Nordwind Logistics GmbH."),
    ("Have they paid late before?", "Yes. Two of their last five invoices were paid after the due date, by 6 and 11 days."),
    ("Draft a short reminder email.", "Subject: Reminder for INV-204. Dear Nordwind team, ..."),
    ("Make it a bit more formal.", "Subject: Payment reminder, invoice INV-204. Dear Sir or Madam, ..."),
    ("Thanks. What was the invoice number again?", "It was INV-204."),
]

messages = [system]
total_billed = 0
for i, (user, reply) in enumerate(turns, start=1):
    messages.append({"role": "user", "content": user})
    sent = count(messages)            # everything goes in again
    total_billed += sent
    messages.append({"role": "assistant", "content": reply})
    print(f"call {i}: {len(messages) - 1:2d} messages sent, {sent:3d} input tokens, running total {total_billed}")

call 2:  4 messages sent,  58 input tokens, running total 86
call 3:  6 messages sent,  77 input tokens, running total 163
call 4:  8 messages sent, 106 input tokens, running total 269

The two email replies are shortened with "..." on this page to keep the listing readable. The run used the full email texts, which is why calls 5 and 6 jump.

Read the code in three steps:

  • count() encodes each message's text with the tokenizer and adds up the lengths. Real APIs add a few extra tokens per message for the role markers, so true counts are slightly higher.
  • Inside the loop, the user message is appended before counting, because it is part of what gets sent. The reply is appended after, because it does not exist until the model has answered.
  • len(messages) - 1 is the number of messages in the request at that moment: everything except the reply that was just added.

Two details matter

The chart shows two different problems. One is about money, the other is about a hard limit.

1
Cost grows faster than the conversation

Each call pays for every earlier message again. If every turn adds roughly the same number of tokens, call n sends about n times that amount, so the total over a conversation grows roughly with the square of its length. Ten turns cost far more than twice five turns.

In the run above, the six calls together billed 664 input tokens, almost three times the 232 tokens of the final conversation. Long chat sessions, agents that loop many times, and big documents kept in the history are where GenAI bills come from.

2
The context window is a ceiling, not a target

The growing request will eventually hit the model's context window. Before that, two softer problems appear: every call gets slower (more prefill, Lesson 1.2) and models tend to use information in the middle of a very long context less reliably than information near the start or end (the "lost in the middle" effect from the Preview lesson).

So applications do not just keep everything. They decide what to keep, which is the next section.

+Prompt caching: paying less for the repeated part Extra

Since every call repeats the same beginning (system message, tool definitions, earlier messages), several providers offer prompt caching: the provider keeps the processed form of a prompt prefix for a short time, and if the next request starts with exactly the same tokens, that part is processed faster and billed at a lower rate.

  • The cache matches from the very first token. One changed character early in the prompt (a timestamp in the system message, for example) breaks the match for everything after it.
  • Order the request from stable to variable: fixed instructions and tool definitions first, then reference documents, then history, then the new message.
  • Details differ by provider: some cache automatically above a minimum length, others need you to mark cache points. Check the pricing page of the API you use.
★
Industry note

Caching does not change what the model sees; it only changes what you pay and how long prefill takes. The model is still stateless. The provider is caching computation, not memory.

4Managing memory: keep, trim, summarise, retrieve

The simplest strategy is a sliding window: always keep the system message, then add the newest messages until a token budget is used up.

trim.py
import tiktoken

enc = tiktoken.get_encoding("o200k_base")
tokens = lambda m: len(enc.encode(m["content"]))

def fit_to_budget(messages, budget):
    """Keep the system message, then as many of the newest messages as fit."""
    system, rest = messages[0], messages[1:]
    kept, used = [], tokens(system)
    for m in reversed(rest):
        if used + tokens(m) > budget:
            break
        kept.append(m)
        used += tokens(m)
    return [system] + kept[::-1], used

messages = [
    {"role": "system", "content": "You are a helpful assistant for the finance team."},
    {"role": "user", "content": "What is the status of invoice INV-204?"},
    {"role": "assistant", "content": "INV-204 is unpaid. The balance is 1,250.00 EUR and it was due on 3 November."},
    {"role": "user", "content": "Who is the customer?"},
    {"role": "assistant", "content": "The customer on INV-204 is Nordwind Logistics GmbH."},
    {"role": "user", "content": "What was the invoice number again?"},
]
kept, used = fit_to_budget(messages, budget=45)
for m in kept:
    print(f"{m['role']:9} {m['content']}")
print("tokens used:", used)
Output · real run
system    You are a helpful assistant for the finance team.
user      Who is the customer?
assistant The customer on INV-204 is Nordwind Logistics GmbH.
user      What was the invoice number again?
tokens used: 35
  • The loop walks the history backwards (reversed), so the newest messages are considered first.
  • It stops at the first message that does not fit, instead of skipping it and trying older ones. Skipping would leave gaps in the conversation, which confuses the model more than a clean cut.
  • kept[::-1] flips the kept messages back into time order before they are sent.
!
Look at what was dropped

The first question and the first answer (the balance, 1,250.00 EUR) are gone. The last question still works only because the second reply happened to repeat "INV-204". Ask "what was the balance?" and this app would no longer have the answer in the request, so the model would either say it does not know or make a number up. Trimming silently deletes facts.

The main strategies

1
Sliding window

What you just saw. Simple and predictable, with cost capped per call. Its weakness is that old facts disappear, no matter how important they were.

2
Summarisation

When the history gets long, ask a model to summarise the older part, and send the summary instead of the original messages. It keeps the gist in far fewer tokens. The cost: an extra model call, and the summary can lose or distort details (exact amounts, dates, who said what).

3
Structured state

Keep important facts as data, not as chat text: {"invoice_id": "INV-204", "customer": "Nordwind Logistics GmbH"}. The application updates this record and inserts it into every request. Exact values never get trimmed or paraphrased away. This is how serious assistants track "the current case".

4
Retrieval from long-term memory

Store past conversations or notes outside the request, and fetch only the pieces relevant to the new question. It is the same machinery as RAG (Stage 4), applied to your own history. What products call "memory" across sessions is usually this.

StrategyKeepsLosesTypical use
Sliding windowRecent turns, verbatimEverything olderShort support chats
SummarisationThe gist of old turnsExact details; costs a callLong open conversations
Structured stateKey facts, exactlyNothing you trackCase and workflow assistants
RetrievalRelevant old piecesWhat retrieval missesMemory across sessions

Real applications combine them: structured state for the facts that must not be lost, a window of recent turns for flow, and retrieval for anything older.

+"But my API keeps the conversation for me" Extra

Some APIs let you store a conversation on the provider's side and continue it by ID, so your code sends only the new message. That is a convenience in the API, not memory in the model. On each turn the provider rebuilds the full context from what it stored and runs the model on all of it.

  • You still pay for the earlier tokens on each call (caching may reduce the price).
  • The context window still fills up, and the provider applies its own trimming rule when it does, which you then do not control.
  • Your conversation data now lives with the provider, which matters for retention and compliance.

Knowing the mechanism lets you choose deliberately instead of trusting that "it remembers".

5Who is responsible for what

Put sections 1 to 4 together and the division of labour becomes clear. The model is one box in a pipeline; the application owns everything before and after it.

i
The milestone of Stage 1, in one picture

A prediction pipeline is features → model → label, and the model is most of the work. A GenAI application is data, tools, history → request → model → validation → action, and the model is the one part you usually do not build yourself.

6Same input, different output

Your sentiment classifier gives the same label every time you send the same review. A generative model often does not. To see why without an API, here is a tiny toy "model": a table that says which words can follow which, with probabilities. Generation walks the table exactly like the loop in Lesson 1.2.

variance.py
import numpy as np

# a toy "model": the next-token distribution depends only on the last token
table = {
    "<start>": ([" The", " Your", " This"], [0.6, 0.3, 0.1]),
    " The":    ([" invoice", " payment"], [0.7, 0.3]),
    " Your":   ([" invoice", " payment"], [0.5, 0.5]),
    " This":   ([" invoice", " payment"], [0.8, 0.2]),
    " invoice": ([" is", " remains"], [0.6, 0.4]),
    " payment": ([" is", " remains"], [0.7, 0.3]),
    " is":      ([" overdue", " open", " late"], [0.5, 0.3, 0.2]),
    " remains": ([" overdue", " open", " late"], [0.4, 0.5, 0.1]),
}

def generate(rng=None):
    token, out = "<start>", []
    while token in table:
        options, p = table[token]
        token = options[int(np.argmax(p))] if rng is None else rng.choice(options, p=p)
        out.append(str(token))
    return "".join(out).strip()

print("greedy, 3 runs:")
for _ in range(3):
    print("  ", generate())
print("sampling, 5 runs:")
rng = np.random.default_rng(7)
for _ in range(5):
    print("  ", generate(rng))
Output · real run
greedy, 3 runs:
   The invoice is overdue
   The invoice is overdue
   The invoice is overdue
sampling, 5 runs:
   Your payment remains overdue
   The payment is late
   Your invoice is overdue
   The invoice is open
   This invoice remains late
  • table maps the last token to its possible next tokens and their probabilities. A real LLM computes such a distribution with a neural network, over the whole vocabulary, from the whole context; the toy looks only at the last token.
  • generate() loops until it reaches a token with no entry in the table, which plays the role of the end-of-sequence token.
  • Without a random generator it picks the most likely option every time (greedy). With one, it samples.

Greedy gives the same sentence three times. Sampling gives five different sentences from the same "prompt". Note that "The invoice is open" and "The invoice is overdue" are not just different wording: they say different things. Variation is not only cosmetic.

Two sources of variation matter

1
Sampling, which you control

With temperature above 0, every token is a random draw, and one different early token changes everything after it (there is no backspace, Lesson 1.2). For tasks with one right answer (extraction, classification, SQL generation) use a low temperature. For drafting and brainstorming, variety is the point.

2
Tiny numerical differences, which you do not control

Even at temperature 0, hosted models are usually not perfectly repeatable. On GPUs, the order in which floating-point numbers are added can change with how requests are batched together, and floating-point addition is not exactly associative: (a + b) + c can differ from a + (b + c) in the last digits. When two tokens have almost equal logits, that is enough to flip the choice, and the rest of the answer follows the flip. Providers also update models behind the same name.

!
Consequence for testing

A test that compares the model's answer to an exact expected string will fail randomly even when nothing is wrong. GenAI tests must check properties of an answer, not its exact text. That is the next section.

7How you test something that varies

Suppose the app asks the model to extract an invoice into JSON. You cannot predict the exact text, but you know what any correct answer must satisfy: it parses as JSON, it has the required fields, the ID has the right format, the amount is a number. Those are properties, and code can check them every time.

checks.py
import json

def check_invoice_reply(text):
    """Property checks for an extraction reply. Returns a list of failures."""
    try:
        data = json.loads(text)
    except json.JSONDecodeError:
        return ["not valid JSON"]
    problems = []
    for field in ("invoice_id", "amount", "currency"):
        if field not in data:
            problems.append(f"missing {field}")
    if "invoice_id" in data and not str(data["invoice_id"]).startswith("INV-"):
        problems.append("invoice_id has the wrong format")
    if "amount" in data and not isinstance(data["amount"], (int, float)):
        problems.append("amount is not a number")
    return problems

replies = [
    '{"invoice_id": "INV-204", "amount": 1250.0, "currency": "EUR"}',
    '{"invoice_id": "INV-204", "amount": 1250, "currency": "EUR", "note": "due 3 Nov"}',
    '{"invoice": "204", "amount": "1,250.00", "currency": "EUR"}',
    'Sure! Here is the JSON: {"invoice_id": "INV-204"}',
]
for r in replies:
    problems = check_invoice_reply(r)
    print("PASS" if not problems else "FAIL", problems)
Output · real run
PASS []
PASS []
FAIL ['missing invoice_id', 'amount is not a number']
FAIL ['not valid JSON']

The four replies are the kinds a model really produces. The first two are worded differently and both pass, which is what you want: the test accepts every correct answer. The third used a different field name and a formatted string for the amount. The fourth wrapped the JSON in a friendly sentence, which breaks json.loads, a very common failure in practice.

The function returns a list of problems instead of just True or False. When you run it over hundreds of replies, the list tells you which property fails most often, and that tells you what to fix in the request.

The layers of GenAI evaluation

Property checks are the first layer. Each further layer catches more kinds of errors, but costs more per test:

1
Code checks

Like checks.py: valid format, required fields, allowed values, no forbidden content. Free, instant, completely repeatable. Run them on every single reply in production too, not only in tests, and retry or fall back when they fail.

2
Reference answers (a test set)

A fixed set of inputs with known correct outputs, built from real cases: "for this invoice PDF, the amount is 1,250.00". Compare the extracted values, not the full text. This is your regression test: rerun it after every prompt or model change and see whether the score moved.

3
Model as judge

For open-ended answers (summaries, emails) there is no single reference. A second model call can grade the answer against a written rubric: "Does the reply mention the invoice ID? Is every number supported by the source?". Useful at scale, but the judge is itself a model, so check its grades against human grades before you trust it.

4
Human review

People grade a sample of real outputs. Slow and expensive, but it is the ground truth that calibrates the other layers, and it finds problems nobody thought to write a check for.

≈
SQL / Power BI analogy

You already test reports this way. Code checks are like data-quality rules (no nulls in the key, totals reconcile). A reference test set is like comparing a report against figures finance has signed off. Human review is the business user looking at the dashboard. Nobody tests a report by comparing its pixels to a screenshot, and nobody should test an LLM by comparing exact strings.

+Common misconceptions Extra

✕
"The model learns from what I tell it."
Not during use. The weights are fixed. A correction only affects replies while it is still in the request.
✕
"Temperature 0 makes it deterministic."
Much more repeatable, not guaranteed identical on hosted APIs (section 6). Design tests for properties anyway.
✕
"A bigger context window means I can just send everything."
You pay for every token on every call, latency grows, and models use long contexts less reliably. Select, don't dump.
✕
"If the answer is wrong, we need a better model."
Check the request first. Most wrong answers come from missing, outdated or buried information in the context.
✕
"It worked on my five examples, so it works."
Outputs vary and inputs vary more. You need a test set of realistic cases and a score you track over time.

?Check yourself

Q1A user says "the bot remembered my order number from earlier". Where was the order number actually stored?

In the application: in the stored conversation history (or a state record) that the app sent again with the new message. The model read it from the request. It stored nothing itself.

Q2Every turn of a chat adds about 50 tokens. Roughly how do the input tokens of call 20 compare with call 10, and what about the total cost of 20 turns vs 10?

Call 20 sends about twice as many tokens as call 10 (about 1,000 vs 500). The total grows roughly with the square: the sum over 20 calls is about 50 × (1 + 2 + … + 20) = 10,500 tokens, against 50 × (1 + … + 10) = 2,750 for 10 calls. Twice the conversation, nearly four times the input cost.

Q3Your sliding-window app forgets the customer's account number after a long chat. Which strategy fixes this properly, and why not just raise the budget?

Structured state: store the account number as a field and insert it into every request, so it can never be trimmed away. Raising the budget only delays the problem and raises cost and latency on every call.

Q4Why would you put a timestamp at the end of the request rather than in the first line of the system message?

Prompt caching matches the request from the first token. A timestamp at the start changes on every call and breaks the cache for everything after it. At the end, the long stable part before it can still be cached.

Q5A colleague's test asserts reply == "The invoice is overdue.". It passes on Monday and fails on Tuesday with no code change. What happened, and how should the test be written?

The output varied (sampling, numerical differences or a model update), which is normal. Test properties instead: for example, the reply mentions the right invoice ID, states the correct status taken from the data, and stays under a length limit. For structured outputs, parse them and compare the fields.

Q6Name two things the application must do after the model replies, before showing anything to the user.

Any two of: parse and validate the output (format, fields); check the user is allowed to see or do what the reply contains; verify claims or numbers against the source data; store state and log the call for evaluation; decide on a fallback or retry if checks fail.

What to retain from this lesson

The model is a stateless function from a request to text. Memory, knowledge of your data, permissions and quality checks all live in the application around it. Building GenAI products mostly means building that application well.

  • Stateless: the model keeps nothing between calls and its weights do not change during use.
  • Chat memory is the app resending history; input cost per call grows with the conversation, and the total grows roughly with its square.
  • Context construction (instructions, retrieved data, tool results, history, new message) is the main lever on answer quality.
  • Manage history with windows, summaries, structured state and retrieval; trimming silently drops facts.
  • Outputs vary because of sampling and small numerical effects, so test properties, not exact strings.
  • Evaluation has layers: code checks, reference test sets, model judges, human review.
