1.2 From prediction models to generative models

What changes when we move from predicting a label or a value to generating text? Built directly on what you already do with ML and DL.

~35 minModule 1Maths + Python

1Start from a familiar prediction problem

input
review = "The delivery was late, but the product is excellent."

A sentiment classifier outputs a probability for each predefined class:

Positive0.75
Neutral0.20
Negative0.05
P(y | x)x = the review, y = a sentiment label. The app usually picks the most probable one.

A language model also outputs probabilities, but over every token in its vocabulary, given the tokens so far:

"The delivery was" → next token?
" late"0.46
" fast"0.22
" delayed"0.12
all others0.20
Illustrative numbers. Real vocabularies have tens of thousands to a few hundred thousand tokens, so "all others" is a very long tail.
i

Key connection: a text generator is a classifier run in a loop. At each step the "classes" are the vocabulary, and the chosen token is fed back in as input.

2How repeated prediction becomes an answer

Prompt: Explain overfitting in one sentence.

Prompt + Overfitting␣occurs

…⟨end⟩

Token boundaries are illustrative, not from a specific tokenizer. Generation stops at a special end-of-sequence token or a length limit.

At every step the model computes a distribution over the next token:

P(ti | t1, t2, …, ti−1)

A decoding procedure picks one token from it, and that token joins the context for the next step. This is autoregressive generation: each prediction is conditioned on everything before it, including the model's own earlier output.

For an output y1…yT given a prompt x, the chain rule of probability gives:

P(y1, …, yT | x) = ∏i=1T P(yi | x, y1, …, yi−1)Next-token probabilities multiply into a probability for the whole answer.
!

Consequence: there is no backspace. Once a token is chosen, everything after conditions on it. An early wrong token (a wrong number, a wrong name) tends to get "justified" by what follows, which is one reason long answers drift.

+Discriminative vs generative, precisely Extra

These are the formal names for the two kinds of model you now know:

KindModelsExample
DiscriminativeP(y | x): a label given an inputLogistic regression, your sentiment classifier
GenerativeThe data itself: P(x) or P(x, y)Naive Bayes, language models, image generators

A language model is generative because it models the probability of text itself:

P(text) = ∏i P(ti | t<i)

A chat answer is just conditional generation: the same model, with the prompt treated as the first part of the text.

3What the model learns in training

In causal language-model training, every position is trained to predict the token that comes after it. One sentence gives many training examples at once:

SeesMust predict
Thecat
The catsat
The cat saton
The cat sat onthe

The loss is the negative log-likelihood of the true next tokens:

𝓛(θ) = − ∑i log Pθ(ti | t<i) θ = parameters · ti = the true next token · t<i = all tokens before position i

This connects straight to classification: at each position the model predicts one "class" out of a very large vocabulary, and the loss is the same cross-entropy loss you already use for multi-class classifiers. The only difference is that it is applied at every position, then summed (or averaged).

Two details matter

Training and inference handle positions in opposite ways. This difference explains why training is efficient on GPUs and why using the model feels slow for long answers.

1
During training, predictions at many positions are computed in parallel

In training we already have the full sentence The cat sat on the. So the model does not need to wait for anything: it can make all four predictions (after "The", after "The cat", and so on) in one forward pass, and the loss for all of them is computed at once.

There is a catch. If every position could see the whole sentence, the position that must predict "sat" could simply look at "sat" and copy it. The model would learn nothing. So a causal mask is applied: each position is only allowed to see the tokens before it, never the ones after.

Predicting after…Thecatsaton
"The"seeshiddenhiddenhidden
"The cat"seesseeshiddenhidden
"The cat sat"seesseesseeshidden
"The cat sat on"seesseesseessees

The result: all positions are trained at the same time, but each one behaves exactly as if the future did not exist yet. That is the same situation the model will face when it is used for real.

2
During normal (autoregressive) inference, new tokens are produced one at a time

When you use the model, the answer does not exist yet. The model predicts the first output token, a decoding rule picks it, and only then can the model predict the second token, because the second one depends on which first token was chosen.

So generation is a loop: predict → pick → append → predict again. There is no way to compute token 50 before token 49 has been chosen. Training could use parallelism because the answer was known in advance; inference cannot.

★
Why this matters in your apps

A 1,000-token answer needs 1,000 steps of this loop, so long outputs are slow and expensive. This is the root of the latency and cost behaviour covered in the Extra section on latency below, and later in Module 8.

i
In one sentence

Training: the answer is known, so all positions are learned together, and the causal mask stops them from cheating. Inference: the answer is unknown, so tokens must be produced one after another.

Pretraining and post-training

Pretraining is the large next-token training described above, run on huge amounts of text. It establishes the model's language-modelling ability: grammar, facts it has seen often, coding patterns, styles of writing.

Later post-training stages (for example instruction tuning and preference tuning) shape how the model behaves: following instructions, answering in a helpful format, refusing unsafe requests. We study these stages separately in Stage 2.

+Base models vs instruction-tuned models Extra

Pretraining alone gives a base model: an excellent text continuer that does not know it is supposed to answer you. Ask it What is the capital of France? and it may continue with more quiz questions, because that is what such a line often precedes on the web.

Post-training produces an instruction-tuned (chat) model that treats your text as a request and answers it. Almost every API model you will call is this kind.

★
Why it matters at work

Open-weight model families are often released in both versions (e.g. a name ending in "-base" and one ending in "-instruct" or "-chat"). Pick the instruct version for applications; the base version is mainly a starting point for your own fine-tuning.

4Why this changes application design

A
"Explain what an invoice is."
The model can answer from patterns learned in training.
B
"What is the outstanding balance on invoice INV-204?"
The app must fetch the actual record. Generation alone cannot know the current balance; it can only produce a plausible-looking number.
1
Engineering principle #1

A model's ability to generate an answer is separate from the application's ability to supply evidence for it.

Model behaviourApplication responsibility
Produces plausible continuationsSupply relevant, authorised information
Can state something falseCheck claims against evidence where it matters
Produces text that resembles JSONParse and validate the output

Answers of varying qualityEvaluate against task-specific criteria
≈
SQL / Power BI analogy

Question B is a lookup: SELECT balance FROM invoices WHERE id = 'INV-204'. You would never let a report estimate that figure. In a GenAI app, the model phrases the answer around the queried value; it is never the source of the value.

+Why fluent is not the same as true Extra

Look at the loss again: it rewards assigning high probability to text that looks like the training data. Nothing in it checks facts. So when the model lacks the knowledge, the most likely continuation is still a confident, well-formed sentence, just with wrong content. This is what people call hallucination.

Three root causes you will meet in practice:

  • Missing knowledge: private data (your invoices) or events after the training cutoff.
  • Pattern over fact: a rare fact loses to a common-looking pattern, e.g. inventing a citation in the right format.
  • No abstention by default: "I don't know" is only produced if training or your prompt makes it likely.

5Python experiment: picking a token

This code isolates how a next token can be selected after a model has produced probabilities. It uses a hand-written distribution, so you can understand the selection step without loading an LLM. Here is the full script, then a line-by-line walkthrough.

decode.py
import numpy as np

# candidate next tokens for "The capital of France is"
tokens = np.array([" Paris", " Lyon", " Berlin", "."])
probabilities = np.array([0.85, 0.08, 0.05, 0.02])

# greedy: always take the most probable token
greedy_token = str(tokens[np.argmax(probabilities)])
print("Greedy:", repr(greedy_token))

# sampling: draw according to the distribution
rng = np.random.default_rng(seed=42)
samples = rng.choice(tokens, size=20, p=probabilities)
print("Samples:", samples.tolist())
Output · real run
Greedy: ' Paris'
Samples: [' Paris', ' Paris', ' Lyon', ' Paris', ' Paris', ' Berlin', ' Paris', ' Paris', ' Paris', ' Paris',
          ' Paris', ' Lyon', ' Paris', ' Paris', ' Paris', ' Paris', ' Paris', ' Paris', ' Paris', ' Paris']

Step 1 · Import NumPy

NumPy provides arrays, numerical operations and random sampling. Here it stores the candidates, finds the largest probability, and draws the samples.

Step 2 · Define candidate tokens and their probabilities

The two arrays line up by position: index 0 of tokens goes with index 0 of probabilities, and so on.

IndexCandidate tokenProbability
0" Paris"0.85
1" Lyon"0.08
2" Berlin"0.05
3"."0.02

The probabilities sum to 1, as a probability distribution must. NumPy's choice raises an error if they do not.

The leading spaces in " Paris" and the other city names are intentional. Many tokenizers store a space together with the word that follows it as a single token. With a real tokenizer, " Paris" and "Paris" are two different tokens with different IDs; Lesson 2.1 shows this with real output.

A real model does not hand you probabilities directly. It produces logits (one raw score per vocabulary entry), and a softmax converts those scores into probabilities. Here we skipped that and wrote the probabilities by hand. The Extra section below shows the softmax step.

Step 3 · Select the most probable token (greedy decoding)

The greedy line does two things at once. Split apart, it reads:

greedy, step by step
best_index = np.argmax(probabilities)   # 0
greedy_token = tokens[best_index]        # " Paris"
  • argmax returns the index of the largest value, not the value itself. The largest probability is 0.85 at index 0, so it returns 0.
  • That index is then used to look up the token in the same position.

Always taking the highest-probability next token is called greedy decoding.

repr() prints the string with its quotation marks, which makes the leading space visible: ' Paris' instead of a bare Paris. The extra str() is only there because NumPy 2 would otherwise print np.str_(' Paris').

!
Greedy is local

Greedy makes the best choice for this one step. It does not guarantee the most probable complete answer, because a slightly less likely token now can lead to a much more likely sentence later. It also never guarantees a factually correct answer: if the model ranks a wrong token highest, greedy picks it every time.

Step 4 · Create a reproducible random generator

np.random.default_rng(seed=42) creates a pseudorandom number generator: an algorithm that produces numbers which look random but are fully determined by its starting state.

  • The seed sets that starting state. Recreate the generator with the same seed, in the same environment, and you get exactly the same samples. That makes experiments reproducible.
  • The number 42 has no special meaning; any integer works.
  • Each call to rng.choice() advances the generator's state, so calling it again draws a new set of samples.

Step 5 · Sample according to the probabilities

  • tokens: the candidates to choose from.
  • size=20: make 20 selections.
  • p=probabilities: how likely each candidate is to be picked.

Sampling is with replacement by default, so the same token can appear many times. .tolist() converts the NumPy array into a normal Python list for printing.

Across many draws, about 85% would be ' Paris'. In only 20 draws you should not expect exactly 17. This run happened to give 17 Paris, 2 Lyon and 1 Berlin, but another seed could give 15 or 19. Probabilities describe the sampling process; they are not fixed quotas.

Notice that sampling returned ' Berlin' once. A possible token is not necessarily a correct one.

!
One essential distinction: 20 samples are not a 20-token sentence

These are 20 independent selections for the same next-token position, all drawn from one fixed distribution. Nothing was appended, and the distribution never changed.

Real autoregressive generation is a loop in which the model recomputes the distribution after every chosen token:

conceptual pseudocode
for step in range(max_new_tokens):
    probabilities = model(context)           # new distribution every step
    next_token = select_token(probabilities)  # greedy or sampling
    context.append(next_token)               # the choice becomes input
    if next_token == END_OF_SEQUENCE:
        break

Our experiment is only the select_token line, studied on its own.

+Where the probabilities come from: logits and temperature Extra

The network does not output probabilities directly. Its last layer outputs one raw score per vocabulary token, called a logit. Softmax turns logits into probabilities, exactly as in your multi-class classifiers:

pk = exp(zk / T) / ∑j exp(zj / T)z = logits · T = temperature (normal softmax is T = 1)

Temperature divides the logits before softmax. Below 1 it sharpens the distribution (closer to greedy); above 1 it flattens it (more variety, more risk). Tap the buttons:

" Paris"0.856
" Lyon"0.078
" Berlin"0.047
"."0.019
Logits [4.0, 1.6, 1.1, 0.2]. Values are from the code below.
temperature.py
import numpy as np

logits = np.array([4.0, 1.6, 1.1, 0.2])  # Paris, Lyon, Berlin, "."

for T in [0.5, 1.0, 2.0]:
    z = logits / T
    p = np.exp(z - z.max())   # subtract max for numerical stability
    p /= p.sum()
    print(T, np.round(p, 3).tolist())
Output · real run
0.5 [0.988, 0.008, 0.003, 0.0]
1.0 [0.856, 0.078, 0.047, 0.019]
2.0 [0.593, 0.179, 0.139, 0.089]

At T = 2, " Berlin" goes from about 5% to about 14%. As T approaches 0, sampling becomes greedy. That is why low temperature is the usual choice for extraction, classification and code, and higher temperature for brainstorming. Other decoding settings (top-p, top-k) come in Stage 2.

+Why everything is done in log space Extra

The chain rule multiplies many probabilities below 1. For long outputs that product underflows to zero in floating point, so models and APIs work with log-probabilities and add them instead.

logprobs.py
import math

# per-token probabilities for a short 4-token answer
step_probs = [0.9, 0.7, 0.8, 0.6]
print(math.prod(step_probs))                      # 0.3024
print(sum(math.log(p) for p in step_probs))     # -1.196 (same information, as a sum)

# a 2000-token answer where each step has probability 0.5
print(0.5 ** 2000)              # 0.0  -> underflow, information lost
print(2000 * math.log(0.5))     # -1386.29  -> still usable

Why you will care later: many APIs can return per-token logprobs, which are handy as confidence signals for classification-style prompts and for evaluation. The training loss in section 3 is simply the negative of this sum.

+Sequential decoding has a price: latency and cost Extra

The two details from section 3 show up again inside a single API call. Inference actually has two phases:

1
Prefill: reading your prompt

Your whole prompt is already known, just like the sentence in training. So the model processes all prompt tokens in parallel. This is fast per token, but a very long prompt (big documents, long chat history) still takes noticeable time. It decides how long you wait before the first word appears, called time to first token.

2
Decode: writing the answer

The answer is unknown, so output tokens come out one at a time through the predict → pick → append loop. Each step is a full pass through the model, so output tokens are much slower per token than prompt tokens.

Putting the two together gives a simple model of how long a response takes:

latency ≈ time to first token + (output tokens × time per output token)
  • Long answers are slow answers. Asking for a concise reply or a compact JSON object is a real performance lever.
  • Streaming shows tokens as they are produced. It does not reduce total time, but users see progress after the first token.
  • Providers usually charge more per output token than per input token, which matches the cost difference above.
★
Industry note

When a GenAI feature feels slow, measure time-to-first-token and output length separately before changing models. Often the fix is a shorter output, not a faster model. Covered in Module 8.

?Check yourself

Q1Why can't an LLM on its own reliably answer "What is the balance on INV-204?"

The balance is a private, changing business fact that was never in the training data. The model can only produce a plausible continuation, which may be a made-up number. The app must query the record (tool or retrieval) and pass it in as context.

Q2Training processes positions in parallel, but inference is sequential. Why?

In training the full target text is known, so every position's next token is available at once; the causal mask hides the future. In inference the next token does not exist until it has been chosen, so each step waits for the previous one.

Q3You need repeatable output for a test. What decoding setting, and what is the catch?

Temperature 0 (greedy), or a fixed seed where the provider supports one. The catch: hosted APIs can still vary slightly across hardware, batching and model versions. That is why GenAI tests check properties of an answer (valid JSON, correct fields, cites the source) instead of exact strings. Module 6.

Q4How is the LLM training loss related to the loss of your sentiment classifier?

It is the same cross-entropy. The classifier applies it once per example over a few classes. The language model applies it at every position over the whole vocabulary, then sums or averages.

Q5A user complains a summary feature takes 12 seconds. Name two things to check before switching models.

(1) Output length: a 1,000-token summary decodes far slower than a 150-token one, so cap or tighten it. (2) Time to first token: a huge prompt makes prefill slow, so trim the context. Also consider streaming so the user sees progress.

Q6Which temperature would you use to extract invoice fields into JSON, and why?

Low, 0 or close to it. Extraction has one correct answer, so you want the most likely tokens, not variety. Higher temperature only adds chances of a wrong digit or broken JSON.

What to retain from this lesson

An autoregressive LLM generates text through repeated next-token prediction. Its training objective teaches it to model sequences of text; that objective alone does not guarantee factual correctness or the successful completion of a business task.

Your work as a GenAI application developer is to connect this probabilistic component to data, tools and controls that make the overall system useful and measurable.

  • An LLM generates text by repeated next-token prediction; each choice is fed back in.
  • Next-token probabilities multiply (in practice, log-probs add) into the probability of a whole answer.
  • Training uses per-position cross-entropy. It rewards likely text, not true text.
  • Logits → softmax with temperature → decoding rule (greedy or sampling) → token.
  • Decoding is sequential, so output length drives latency and cost.
  • Your job: connect this probabilistic component to data, tools and checks that make the system reliable and measurable.
