2.2 Embeddings

A token ID is just a row number. An embedding is what sits in that row: a list of learned numbers that lets the model treat similar tokens in similar ways. This lesson builds the idea from scratch and trains real embeddings in NumPy.

~45 minStage 2Real training runPython + NumPy

1The problem: an ID carries no meaning

After lesson 2.1, the text " Paris" has become the integer 12650. The network does arithmetic, so the question is: what numbers do we actually feed it for that token? There are three candidates, and only the third works.

1
Feed the ID itself as a number

The network would treat 12650 as a quantity. It would "think" token 12651 is almost the same as token 12650 and that token 25300 is twice as much of something. None of that is true: IDs were handed out by the tokenizer in merge order, so neighbouring IDs are unrelated pieces of text. Any pattern the network learned from the size of the number would be noise.

2
Feed a one-hot vector

A one-hot vector is a list as long as the vocabulary, all zeros except a single 1 at the token's position. It removes the fake ordering, but it has two problems. It is huge: 200,019 numbers for every token in o200k_base. And every pair of tokens is exactly as different as every other pair: " Paris" is as far from " London" as it is from " banana". The model would have to learn everything about each token separately, with no way to share what it learned about one city with another.

3
Feed a short list of learned numbers: an embedding

Give every token its own list of d numbers (a few hundred to a few thousand), and let training choose them. Tokens that behave alike end up with similar lists, so whatever the model learns about " Paris" partly carries over to " London". This list is the token's embedding, and d is the embedding dimension.

i

Definition. An embedding is a vector (a fixed-length list of numbers) that represents an item, here a token, so that items used in similar ways have similar vectors. The numbers are parameters: they start random and are learned during training.

≈
SQL / Power BI analogy

The token ID is the surrogate key. The embedding table is the dimension table it points to, except that its columns are not "Country" or "Population". They are d unnamed numeric columns whose values were filled in by training, and two rows are "alike" when their numbers are alike.

2The lookup: taking one row of the table

All the embeddings live in one matrix, the embedding table, with one row per vocabulary entry and one column per dimension: shape (V, d). Turning a token into its embedding means reading row number id. Nothing is computed; it is a read.

There is one useful way to see this read as maths. Multiplying a one-hot vector by the table picks out exactly one row, because every row is multiplied by 0 except the one multiplied by 1. So the lookup is a matrix multiplication, just done the cheap way. That is why the embedding table can be trained with the same gradient machinery as every other layer.

lookup.py
import numpy as np

rng = np.random.default_rng(0)
V, d = 6, 4                      # tiny vocabulary, tiny vectors
E = rng.normal(size=(V, d)).round(2)

token_id = 3
one_hot = np.zeros(V)
one_hot[token_id] = 1

print("row 3:        ", E[token_id])
print("one-hot @ E:  ", one_hot @ E)
print("same numbers: ", np.array_equal(E[token_id], one_hot @ E))

ids = [3, 0, 3, 5]               # a 4-token input
X = E[ids]
print("input shape:  ", X.shape)
print("rows 0 and 2 equal:", np.array_equal(X[0], X[2]))
Output · real run
row 3:         [-2.33 -0.22 -1.25 -0.73]
one-hot @ E:   [-2.33 -0.22 -1.25 -0.73]
same numbers:  True

Reading the output

  • E[token_id] and one_hot @ E give the same four numbers. Real frameworks always do the first, because building a 200,019-long one-hot vector per token would waste memory and time.
  • A 4-token input becomes a (4, 4) matrix: one row per token, one column per dimension. For real models that is (n, d), the shape the transformer layers receive.
  • Rows 0 and 2 are identical because both positions hold token 3. The lookup does not know where a token sits or what is around it. Position and context are added later (section 6 and the next lessons).
!
A row number and a row are different things

Lesson 2.1 said token IDs carry no meaning. That is still true. The meaning lives in the row the ID points to, not in the ID. Swap the table for another model's table and the same ID points at completely different numbers.

3Measuring "similar": dot product, cosine, distance

"Similar tokens get similar vectors" needs a precise meaning of similar. Think of each embedding as an arrow from the origin. Two arrows can be compared by how long they are and by which way they point. Three measures are in everyday use:

1
Dot product

Multiply the two vectors position by position and add the results: a · b = a₁b₁ + a₂b₂ + …. It is large when the arrows point the same way, zero when they are at a right angle, negative when they point apart. But it also grows with length, so a long vector looks "more similar" to everything.

2
Cosine similarity

The dot product divided by both lengths. That removes length and keeps only direction, so the result always lies between −1 and +1: +1 same direction, 0 unrelated (right angle), −1 opposite. This is the standard measure for comparing embeddings.

3
Euclidean distance

The straight-line distance between the arrow tips. Small means close. It is intuitive, but like the dot product it is sensitive to length, as the run below shows.

cos(a, b) = a · b / (‖a‖ ‖b‖)‖a‖ = the length of a = the square root of the sum of its squared numbers
similarity.py
import numpy as np

a = np.array([2.0, 1.0])
b = np.array([8.0, 4.0])         # same direction as a, four times as long
c = np.array([1.0, -2.0])        # at a right angle to a


def cosine(u, v):
    return u @ v / (np.linalg.norm(u) * np.linalg.norm(v))


for name, v in [("b", b), ("c", c)]:
    print(f"a vs {name}: dot={a @ v:5.1f}  cosine={cosine(a, v):+.2f}  distance={np.linalg.norm(a - v):.2f}")

an, bn = a / np.linalg.norm(a), b / np.linalg.norm(b)
print("after normalising, dot = cosine:", round(float(an @ bn), 2))
Output · real run
a vs b: dot= 20.0  cosine=+1.00  distance=6.71
a vs c: dot=  0.0  cosine=+0.00  distance=3.16
after normalising, dot = cosine: 1.0

Two details matter

1
Length can hide direction

b points exactly the way a does, so cosine says they are identical (+1.00). Distance says the opposite: c, which is at a right angle and shares nothing with a, is closer (3.16 against 6.71). In embeddings, length often reflects things like how frequent a token is, not what it means, which is why cosine is the default.

2
Normalise once, then use the fast dot product

If every vector is scaled to length 1 first, the dot product is the cosine (the last line of the output). Vector databases and many embedding APIs rely on this: they store length-1 vectors and use plain dot products, which are faster. OpenAI's embedding endpoints, for example, already return vectors of length 1.

4How embeddings are learned

Nobody writes the numbers in the table. They start as small random values, so at first every token is a random arrow and similarities are meaningless. Then the model is trained on next-token prediction (lesson 1.2), and the embedding rows are parameters like any others: after each batch, the gradient of the loss says how each used row should move to make the true next token more likely, and the row moves a little.

Why would that make related tokens similar? Because of what the model is asked to do. If "cat" and "dog" are both often followed by "chased", "drank" and "slept", the model can only predict well if their rows produce similar scores for those next words. The cheapest way to do that is to give them similar rows. This idea, that a word is characterised by the contexts it appears in, is called the distributional hypothesis; the linguist J. R. Firth put it as "you shall know a word by the company it keeps" (1957).

Train embeddings yourself

A tiny corpus of 30 sentences about pets, drinks and vehicles. Save it as corpus.py:

sentences = [s.split() for s in corpus if s.strip()]

Now the smallest possible next-word model: look up the current word's row in E, multiply by an output matrix W to get one score (logit) per vocabulary word, apply softmax, and train with the cross-entropy loss from lesson 1.2. Only NumPy, with the gradients written out by hand.

learn_embeddings.py
import numpy as np

from corpus import sentences  # the 30 sentences above
vocab = sorted({w for s in sentences for w in s} | {"<end>"})
ix = {w: i for i, w in enumerate(vocab)}
V, d = len(vocab), 12

# training pairs: (this word, the word that comes next)
pairs = [(ix[s[i]], ix[(s + ["<end>"])[i + 1]]) for s in sentences for i in range(len(s))]
x = np.array([p[0] for p in pairs])
y = np.array([p[1] for p in pairs])

rng = np.random.default_rng(42)
E = rng.normal(scale=0.1, size=(V, d))  # embedding table, starts as random noise
W = rng.normal(scale=0.1, size=(d, V))  # output layer: vector -> one score per word


def cos(a, b):
    u, v = E[ix[a]], E[ix[b]]
    return u @ v / (np.linalg.norm(u) * np.linalg.norm(v))


def report(label):
    print(label, "  ".join(f"{a}/{b} {cos(a, b):+.2f}" for a, b in
                           [("cat", "dog"), ("tea", "coffee"), ("car", "bus"), ("cat", "tea")]))


report("before:")
lr = 1.0
for step in range(3001):
    h = E[x]                                   # look up one row per training example
    logits = h @ W
    logits -= logits.max(axis=1, keepdims=True)
    p = np.exp(logits)
    p /= p.sum(axis=1, keepdims=True)
    loss = -np.log(p[np.arange(len(y)), y]).mean()
    if step in (0, 3000):
        print(f"step {step}: loss {loss:.2f}")
    g = p
    g[np.arange(len(y)), y] -= 1               # gradient of the loss w.r.t. the logits
    g /= len(y)
    gW = h.T @ g
    gh = g @ W.T
    W -= lr * gW
    np.add.at(E, x, -lr * gh)                  # only the rows that were used get updated
report("after: ")


def nearest(w, k=3):
    v = E[ix[w]]
    sims = E @ v / (np.linalg.norm(E, axis=1) * np.linalg.norm(v))
    return [vocab[i] for i in np.argsort(-sims) if vocab[i] != w][:k]


for w in ["cat", "tea", "bus", "morning"]:
    print(w, "->", nearest(w))
words = ["cat", "dog", "tea", "coffee", "car", "bus"]
print("matrix", [[round(float(cos(a, b)), 2) for b in words] for a in words])

Reading the output

  • Before training the similarities are random (car/bus is even −0.36). The vectors carry no knowledge yet.
  • The loss starts at 4.25, which is ln(70): with 70 vocabulary entries (69 words plus <end>), random guessing gives each word a 1-in-70 chance. It falls to 0.85 as the model learns what tends to come next.
  • After training cat/dog, tea/coffee and car/bus all point roughly the same way (+0.55 to +0.79), while cat/tea stays near zero (−0.10). The categories were never given to the model. They came out of next-word prediction alone.
  • Each word's nearest neighbour is right (cat → dog, tea → coffee, bus → car), but the next ones are noise ("was", "barked", "light"). Thirty sentences is far too little data for more.
  • "morning" gets poor neighbours (floor, tree, lazy). It appears in only two sentences, so its row was updated only a few times. Real models have the same weakness for rare tokens, which is one of the costs of a very large vocabulary (lesson 2.1).
★
From toy to real

Real LLMs do exactly this, at a different scale: a vocabulary of 100k to 200k tokens, d in the thousands, trillions of training tokens, and a deep transformer between the lookup and the output layer instead of nothing. The embedding table is trained together with everything else, in the same loop.

+
Extra · word2vec and the famous analogy

Before LLMs, embeddings were trained on their own. word2vec (Mikolov et al., 2013) trained a model like ours to predict nearby words and became famous for analogies: the vector for king − man + woman lands near queen.

Treat that with care. The published results exclude the three input words from the answers (otherwise the nearest vector is often "king" itself), and the trick works for some relations, such as capitals and verb tenses, far better than for others. It shows that some directions in the space line up with real relations, not that embeddings do reliable reasoning.

5How big the table is

The table holds V × d parameters, and both numbers are large in real models:

ModelVocabulary VDimension dTable V × d
GPT-2 small (2019)50,25776838,597,376 (about 31% of its 124M parameters)
Llama 3 8B (2024)128,2564,096525,336,576 (about 6.5% of 8B)
o200k vocabulary, d = 4,096 (illustrative)200,0194,096819,277,824

Two things follow. In small models the embedding table is a big share of all parameters, so the vocabulary size is a real design cost. And because the table stores numbers for every token, the same text costs more memory to represent in a model with a bigger d, but each token's row can also hold more.

!
Choosing d is a trade-off, not "bigger is better"

A small d forces unrelated tokens to share directions. When we tried d = 2 with a counting method on this same corpus (not shown), "cat" and "car" came out identical (cosine 1.00): two numbers cannot separate three categories plus everything else. A larger d gives room but costs memory, compute and data to fill. Model designers choose d together with the depth and width of the whole network.

+
Extra · weight tying

The output layer that turns a final vector into one score per token is also a (d, V) matrix, as big as the embedding table. Some models, GPT-2 among them, use the same matrix for both jobs, which is called weight tying. It saves parameters and fits the intuition that "this vector means token X" should work in both directions. Many larger models keep two separate matrices instead.

6Static rows, contextual meaning

The table gives a token the same row in every sentence. "bank" in "river bank" and "bank" in "bank account" start from identical numbers. That is a static embedding: one vector per token, no matter the context.

The transformer layers that follow fix this. Each layer mixes information between positions (that is what attention does, the topic of the coming lessons), so after a few layers the vector at the position of "bank" reflects its neighbours. These context-dependent vectors are called contextual embeddings or hidden states.

!
Why this matters in practice

The raw rows of an LLM's embedding table are not a good search index. They know nothing about the sentence, and one word is often several tokens. When an application needs a vector that represents what a whole text means, it uses a model built for that job, which is the next section.

7Token embeddings vs text embeddings

The word "embedding" is used for two different things, and mixing them up causes real confusion in RAG projects.

1
Token embeddings: one row per token, inside a model

What this lesson built. They are the first step inside every LLM, you never see them through an API, and they are not stored anywhere in your application.

2
Text embeddings: one vector per whole text, from an embedding model

An embedding model (usually an encoder, lesson 1.4) reads a whole sentence, paragraph or chunk through all its layers and returns one vector for it, often by averaging the contextual vectors of all positions. It is trained specifically so that texts with similar meaning get high cosine similarity, typically on pairs like a question and its answer. This is what RAG stores and searches.

concept.py · not runnable yet
# concept only: every provider names this differently
chunks = ["How to reset a password", "Refund policy for annual plans", "Changing your email address"]
chunk_vectors = embedding_model.embed(chunks)        # shape (3, d), stored once

query_vector = embedding_model.embed(["I forgot my password"])[0]
scores = chunk_vectors @ query_vector                # cosine, if the vectors have length 1
best = chunks[scores.argmax()]

Rules that save real projects:

  • Only compare vectors from the same model. Two embedding models produce unrelated spaces, even when the dimension matches. Changing the model means re-embedding every stored chunk.
  • The dimension is fixed by the model. Your vector database index is created for that dimension.
  • Similar is not the same as correct. A chunk can be close to the question and still not contain the answer. Retrieval quality is measured, not assumed; that is Stage 4.
≈
SQL / Power BI analogy

Keyword search is WHERE text LIKE '%password%': it finds rows that share the exact word. Embedding search ranks rows by meaning, so "I forgot my password" can match a chunk titled "How to reset a password" even with few shared words. In practice teams often use both together.

?Check yourself

Q1Why not feed the token ID straight into the network as a number?

The network would treat the size of the ID as meaningful: 12651 would look "almost the same" as 12650. IDs are arbitrary row numbers, so that pattern would be noise. The ID is only used to pick a row.

Q2In a 4-token input, the same token appears twice. Are its two rows after the lookup the same or different? And after the transformer layers?

The same after the lookup (rows 0 and 2 in lookup.py). Usually different after the layers, because the layers mix in each position's neighbours and position. The lookup is static; the layers make the vectors contextual.

Q3Vector b is a, doubled in length. What are their cosine similarity and their dot product compared to a with itself?

Cosine similarity is +1, exactly as for a with itself, because the direction is the same. The dot product doubles, because it grows with length. That is why cosine is used when only direction (meaning) should count.

Q4In learn_embeddings.py nobody labelled cat and dog as animals. Why did their rows become similar?

Both are followed by the same words ("chased", "drank", "slept"). To predict those next words well, their rows must produce similar scores, and training moved them towards each other. Similar contexts lead to similar embeddings: the distributional hypothesis.

Q5Your team switches from embedding model A to model B with the same dimension, and keeps the stored vectors from A. What happens?

Searches return nonsense. A query embedded with B is compared against chunks embedded with A, and the two spaces are unrelated even though the vectors have the same length. Every chunk has to be re-embedded with B.

Q6Why did "morning" get worse neighbours than "cat" in the training run, and what is the real-model version of this problem?

"morning" appears in only two sentences, so its row was updated far less often and stayed close to its random start. In real models, rare tokens (and rare vocabulary entries in very large vocabularies) get fewer training examples and weaker embeddings.

What to retain from this lesson

An embedding is a learned vector per token, stored as one row of a (V, d) table. The token ID only picks the row; the meaning is in the numbers, and those come from training.

  • The lookup is a read of one row, mathematically the same as a one-hot vector times the table.
  • Cosine similarity compares direction and ignores length; with length-1 vectors it equals the dot product.
  • Rows start random and next-token training pulls tokens that appear in similar contexts together.
  • The table is static: the same token gets the same row everywhere. Transformer layers make it contextual.
  • Text embeddings for RAG are one vector per whole text from a dedicated embedding model. Only compare vectors from the same model.
