2.1 Tokens and tokenization

Before an LLM can process text, the text has to become numbers. How that happens decides your context budget, your bill, and some surprising model failures.

~40 minModule 1Real tokenizer outputPython

1From text to numbers

A neural network can only do arithmetic on numbers. So every piece of text you send goes through this input pipeline first:

Text→Tokenizer→Token IDs→Embedding lookup→Transformer

The output path runs the other way: the model generates token IDs one at a time, and the tokenizer's decoder turns those IDs back into text.

Transformer→Next token ID→Tokenizer decode→Text you see

This lesson covers the first box, the tokenizer. The embedding lookup gets its own lesson next.

≈
SQL / Power BI analogy

The tokenizer works like a lookup to a dimension table's surrogate key. The text "Paris" is replaced by an integer key such as 12650. That key identifies a row, but the number itself carries no meaning, just like CustomerKey = 4711 says nothing about the customer.

2What exactly is a token?

Definition: a token is one entry in a tokenizer's vocabulary, the fixed list of text pieces the tokenizer knows. Each entry has an integer ID.

Depending on the tokenizer and the input, a token can be:

  • A complete word, e.g. Hello.
  • Part of a word, e.g. ievable.
  • Punctuation, e.g. !.
  • Whitespace joined to the following text, e.g. " world" (with its leading space).
  • A byte or a sequence of bytes, which is how unusual characters and other scripts are covered.
  • A special token: a marker the model uses internally, such as "end of text" (section 7).

i

Tokens are not words and not characters. Token boundaries depend on the particular tokenizer, so the same text can have different token counts on different models.

3Why use pieces of words?

A tokenizer designer has to choose the unit text is cut into. There are three options, each with a real trade-off:

1
Characters or bytes

A tiny vocabulary (there are only 256 possible byte values), and any text at all can be represented, in any language. The cost: sequences get very long. "Hello world" becomes 11 units instead of 2, and since the model processes every unit, long sequences are slow and use up the context window.

2
Whole words

Short sequences for familiar words. But the vocabulary would need every word form in every language (run, runs, running, runner…), and any word not in the list, such as a new product name or a typo, has no representation at all.

3
Subword pieces (what modern LLMs use)

Common words get a single token, while rare words are built from reusable pieces. "running" might be one token, while a rare word is split into a few familiar pieces. The downside is that boundaries can be unintuitive, and efficiency varies by input: plain English is cheap, while code, numbers and many other languages cost more.

Summary of the trade-off:

RepresentationAdvantageLimitation
Characters / bytesSmall vocabulary, covers any textLong sequences
Whole wordsShort sequences for familiar wordsHuge vocabulary, fails on unseen words
SubwordsReuses pieces across many wordsUnintuitive boundaries, uneven efficiency

Why this matters for code

A programmer sees customer_transaction_reconciliation_status as one name. A real tokenizer sees five tokens:

o200k_basecustomer

_status

Notice that the underscore is attached to the following piece, just as a space is attached to the following word in normal text. Long identifiers, URLs and UUIDs are token-expensive, which matters when you paste large code files or logs into a prompt.

+The vocabulary size trade-off Extra

Why not just make the vocabulary huge so everything is one token? Because the vocabulary size V appears inside the model twice:

  • The embedding table has one row per token: V × d numbers, where d is the embedding size.
  • The output layer produces one logit per token at every step, so softmax runs over all V entries.
200,019 × 4,096 = 819,277,824o200k's real vocabulary size × an illustrative embedding size: about 0.8 billion parameters for the embedding table alone

A bigger vocabulary gives shorter sequences (faster, more text per context window) but a bigger, more expensive model, and rare tokens get fewer training examples each. Recent tokenizers have grown (cl100k ≈ 100k entries → o200k ≈ 200k) partly to handle more languages efficiently; you will see the effect on Telugu in section 6.

4How a tokenizer gets its vocabulary: BPE

The vocabulary is not written by hand. It is learned once from a large text corpus, before the model itself is trained. The most common method is Byte Pair Encoding (BPE):

  1. Start with the smallest units: characters, or in modern tokenizers, raw bytes.
  2. Count every pair of neighbouring units across the corpus.
  3. Merge the most frequent pair into a new single unit and add it to the vocabulary.
  4. Repeat thousands of times, until the vocabulary reaches the target size.

The output is two things: the vocabulary, and the ordered list of merge rules. For example, repeated merges could build "t" + "h" → "th", then "th" + "e" → "the".

Run BPE yourself

This is a complete, simplified BPE trainer in plain Python, no libraries needed. The corpus is four words with how often each appears; </w> marks the end of a word, so the trainer can learn word endings.

bpe_toy.py
from collections import Counter

# word -> how often it appears in our tiny "corpus"
corpus = {"low": 5, "lower": 2, "newest": 6, "widest": 3}

# start with every word split into characters, plus an end-of-word marker
words = {tuple(w) + ("</w>",): n for w, n in corpus.items()}


def pair_counts(words):
    counts = Counter()
    for symbols, n in words.items():
        for a, b in zip(symbols, symbols[1:]):
            counts[(a, b)] += n
    return counts


def merge(words, pair):
    merged = {}
    for symbols, n in words.items():
        out, i = [], 0
        while i < len(symbols):
            if i < len(symbols) - 1 and (symbols[i], symbols[i + 1]) == pair:
                out.append(symbols[i] + symbols[i + 1])
                i += 2
            else:
                out.append(symbols[i])
                i += 1
        merged[tuple(out)] = n
    return merged


for step in range(1, 7):
    best, count = pair_counts(words).most_common(1)[0]
    words = merge(words, best)
    print(f"merge {step}: {best[0]!r} + {best[1]!r} (seen {count}x)")

print()
for symbols in words:
    print(symbols)

merge 3: 'est' + '</w>' (seen 9x)
merge 4: 'l' + 'o' (seen 7x)
merge 5: 'lo' + 'w' (seen 7x)
merge 6: 'n' + 'e' (seen 6x)

('low', '</w>')
('low', 'e', 'r', '</w>')

('w', 'i', 'd', 'est</w>')

Reading the output

  • Merges 1–3 build est</w>: "es" appears 9 times (6 in newest + 3 in widest), so it wins first. The tokenizer has discovered the suffix "-est" purely from counting.
  • Merges 4–5 build low, shared by "low" and "lower" (5 + 2 = 7).
  • Now "low" is a single token, while "lower" is low + e + r. With more merges, er would eventually form too.

Frequent pieces become single tokens; rare words stay split. That is exactly the subword behaviour from section 3, emerging from a dozen lines of code.

!
Training the tokenizer happens once; encoding just applies the rules

When you send a prompt, the tokenizer does not learn anything. It applies its fixed merge rules to your text. The vocabulary is frozen together with the model, which is why a model's tokenizer can never be swapped for another one.

Other tokenizer families

Byte-level BPE
BPE that starts from the 256 byte values instead of characters, so any input in any language or encoding can be represented and there is never an "unknown" token. Used by GPT-style models.
WordPiece
A close relative of BPE that picks merges by how much they improve the likelihood of the corpus. Used by BERT; you will meet it in embedding models.
Unigram (usually via SentencePiece)
Starts with a large vocabulary and removes pieces that matter least. SentencePiece also treats spaces as a normal symbol (shown as ▁), so it works for languages without spaces between words.

5Token IDs are identifiers, not meanings

After tokenization, text is a list of integers. Real output from o200k_base:

TextPiecesToken IDs
"Hello world"Hello · " world"[13225, 2375]
" Paris"" Paris"[12650]
"Paris"Paris[72782]

Two things to notice:

  • " Paris" (with a space) and "Paris" are completely different tokens. To the model they are as unrelated as two different words until training has taught it otherwise.
  • The ID 12650 does not express the meaning of Paris mathematically. Nearby IDs are not similar words. The ID is just a row number.

From ID to vector: the embedding table

The model holds an embedding table: a matrix with one learned vector per vocabulary entry. Looking up a token means taking its row:

conceptual shapes
embedding_table.shape == (vocabulary_size, embedding_dimension)

token_vector = embedding_table[token_id]   # one row, length embedding_dimension

For a sequence of n tokens and embedding dimension d, the lookup produces a matrix:

(n, d)one row per token in the input, one column per embedding dimension

Keep three operations separate in your head:

1
Tokenization chooses which vocabulary entries represent the text

Pure string processing, done by fixed rules, outside the neural network.

2
Embedding lookup converts those entries into learned vectors

A table lookup inside the model. The vectors are parameters, learned during training. Meaning starts to live here.

3
Transformer layers process those vectors using the surrounding context

This is where "bank" in "river bank" and "bank account" end up with different representations, even though they start from the same embedding row.

★
Model compatibility

The same ID means different text in different tokenizers. " Paris" is 12650 in o200k_base but 12366 in cl100k_base. Never store token IDs and reuse them with another model; store text.

6Python experiments: four ways to measure length

Experiment A · no install needed

First, see how familiar ways of measuring text disagree with each other:

lengths.py
examples = [
    "Hello world",
    "Hello, world!",
    "customer_transaction_reconciliation_status",
    "నమస్కారం",
]

for text in examples:
    print({
        "text": text,
        "whitespace_words": len(text.split()),
        "unicode_code_points": len(text),
        "utf8_bytes": len(text.encode("utf-8")),
    })
Output · real run
{'text': 'Hello world', 'whitespace_words': 2, 'unicode_code_points': 11, 'utf8_bytes': 11}
{'text': 'Hello, world!', 'whitespace_words': 2, 'unicode_code_points': 13, 'utf8_bytes': 13}
{'text': 'customer_transaction_reconciliation_status', 'whitespace_words': 1, 'unicode_code_points': 42, 'utf8_bytes': 42}
{'text': 'నమస్కారం', 'whitespace_words': 1, 'unicode_code_points': 8, 'utf8_bytes': 24}

What each column measures:

  • whitespace_words: pieces separated by spaces. The identifier is "1 word" even though it is 42 characters long.
  • unicode_code_points: what Python's len() counts. A code point is one entry in the Unicode standard.
  • utf8_bytes: the size when stored or sent as UTF-8. English letters take 1 byte each; each Telugu code point here takes 3 bytes, so 8 code points become 24 bytes.
!

Code points are not visible characters either. నమస్కారం looks like about 5 written characters, but Python counts 8, because vowel signs and the virama (్) are separate code points that combine visually. The same happens with many emoji and accented letters.

What these results teach

1
The same text can cost very different amounts on different tokenizers

One Telugu word is 16 tokens in the older cl100k tokenizer but 5 in o200k. In cl100k, Telugu is mostly split into raw byte fragments. For non-English users this means more cost, slower answers and less room in the context window. It is often called the "token tax", and it depends heavily on the tokenizer.

2
Numbers are chopped into chunks that do not line up with place value

12345678 becomes 123 · 456 · 78. The model never sees "8 digits"; it sees three unrelated tokens. This is one reason LLMs are unreliable at exact arithmetic and digit counting. In applications, do calculations in Python or SQL, not in the model.

3
Plain English is roughly one token per word or punctuation mark

"The invoice INV-204 is overdue." is 6 words but 8 tokens, because - and . are tokens too. Rules of thumb are fine for rough planning, but count with the real tokenizer when limits or cost matter.

Other model families ship their own tokenizers, usually loaded with Hugging Face's AutoTokenizer.from_pretrained(...), and hosted APIs generally provide a way to count tokens for their models. Covered in Stage 3.

+Special tokens and chat templates Extra

Besides text pieces, every vocabulary has a few special tokens that are never produced by normal text. Typical ones:

  • End of sequence / end of text: the model generates this when it is done. It is how the generation loop from Lesson 1.2 knows when to stop.
  • Beginning of sequence: marks the start of the input in some models.
  • Role markers: separate the system instructions, the user's message and the assistant's reply.

A chat API takes a list of messages, but the model only reads one flat token sequence. A chat template joins the messages into that sequence using the special tokens. Conceptually:

what the model actually reads (illustrative format)
<|start|>system
You are a helpful finance assistant.<|end|>
<|start|>user
What is overdue?<|end|>
<|start|>assistant

The exact markers differ for every model family; the shape above is only for illustration. Three practical consequences:

  • The API usually reports a few more input tokens than your text alone, because the template's markers count too.
  • When you run an open-weight model yourself, you must apply its chat template (Hugging Face tokenizers provide apply_chat_template). The wrong template quietly makes answers worse.
  • Role markers are how the model tells instructions apart from user text. This matters for prompt injection (Module 3).

7What tokenization means for applications

1
Context budgeting

Context limits are measured in tokens. Word counts are only rough estimates, and they vary across languages, code and data formats. A budget that works for English documents can overflow on Telugu documents or JSON logs of the same "size".

2
Truncation and chunking

Cutting documents by characters gives chunks of uneven token length. Token-aware chunking (measuring chunk size with the tokenizer) keeps sizes predictable. Size is not everything, though: chunks should also follow the document's structure (headings, paragraphs, functions) so they keep their meaning. Stage 4 goes deep on this.

3
Cost and latency

Hosted APIs bill per token, input and output separately. Input tokens are processed in parallel; output tokens are generated one at a time, so they are slower (see the latency Extra in Lesson 1.2).

4
Model compatibility

Token IDs belong to one tokenizer. Changing models can change token counts, costs and limits even with identical prompts, so re-measure when you switch.

5
Exact-string tasks

Spelling, counting letters, reversing strings, matching identifiers exactly and strict formatting interact awkwardly with token boundaries, because the model never sees individual characters directly. When exactness matters, validate the output in Python (regex, schema checks) instead of trusting the model.

6
Streaming and partial characters Extra

With byte-level tokenizers, one character can be split across tokens. The cl100k run above shows it: decoding Telugu tokens one at a time printed broken "�" symbols, because each token held only part of a character. If you stream raw tokens yourself, buffer bytes until a character is complete. Hosted APIs normally handle this and stream text pieces for you.

7
Whitespace and formatting change the tokens Extra

" Paris" and "Paris" are different tokens. Trailing spaces, odd line breaks or inconsistent casing in prompts and few-shot examples change what the model sees. Keep prompt templates clean and consistent.

?Check yourself

Q1Your English documents fit a 8,000-token budget at about 6,000 words. Can you assume the same word limit for Telugu documents?

No. Other scripts usually need more tokens per word, and how many more depends on the tokenizer (5 vs 16 tokens for one Telugu word in our run). Measure a sample of real documents with the model's tokenizer and set the limit in tokens, not words.

Q2Does the tokenizer learn new words from your prompts?

No. The vocabulary and merge rules were learned once, before model training, and are frozen. A new product name is simply split into existing pieces.

Q3Why is an LLM unreliable at "How many digits are in 12345678?"

It never sees 8 separate digits. It sees tokens like 123, 456, 78, and has to infer the digit count from what it learned about those tokens. Use len(str(n)) in Python for anything exact.

Q4A teammate caches token IDs from one model to save time and reuses them with another model. What goes wrong?

The IDs mean different text in a different vocabulary (" Paris" is 12650 in one tokenizer and 12366 in another), so the second model receives garbage. Cache text, or cache IDs per tokenizer only.

Q5Put these in order and say which one contains learned parameters: transformer layers, tokenizer, embedding lookup.

Tokenizer → embedding lookup → transformer layers. The tokenizer is fixed rules (its vocabulary was learned beforehand, but it has no neural parameters). The embedding table and the transformer layers both hold learned parameters.

Q6In the BPE toy run, why did "e" + "s" get merged before "l" + "o"?

BPE always merges the most frequent pair. "es" appears 9 times (newest × 6 + widest × 3), while "lo" appears 7 times (low × 5 + lower × 2).

What to retain from this lesson

A tokenizer converts text into vocabulary IDs. Those IDs are mapped to embeddings before transformer processing. Token boundaries depend on the tokenizer, so words, characters, bytes and tokens are four different units.

  • Subword tokenizers (mostly BPE) learn their vocabulary once by merging frequent pairs; encoding just applies the rules.
  • Token IDs are row numbers, not meanings, and they are only valid for one tokenizer.
  • Code, numbers and non-English text cost more tokens. Count with the real tokenizer.
  • Special tokens and chat templates turn messages into one sequence; they count against your budget.
  • For exact work (arithmetic, spelling, identifiers), compute or validate in code.
